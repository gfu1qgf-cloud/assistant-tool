复核与修正（仅测试；不改生产 API 调度）
原等待把有界的多次串行工作限在固定总时长内，未区分持续推进与停滞。
现在按 step 观察：10 秒无新步骤立即失败，整轮上限为 20+2*总调用数
秒（最大 80 秒）；超时报告具体步骤与界面状态。仍严格核对 30 次上限、
calls_started/calls_done/complete，以及每个成员自己的服务商／模型／
角色和固定凭据。不是取消截止、重试真实 API 或增加付费调用。
新增虚拟时钟用例：30 步持续推进但共 21 秒可以完成；无进展则在 10 秒
失败，早于旧 15 秒总时限。真正的死等不因新的等待方式被容许。

测试清理也有缺口：普通群聊隐藏窗口本来允许当前请求在后台结束；
原 tearDown 仅检查主窗口及宿主后台队列，却会直接删除子群聊的临时库。
现显式暂停并取消所有子群聊请求，等待生命周期回执清除 handle 后再
关闭、删除临时数据。新增真实假请求用例核对取消、原生结束、无下一次
调用且数据库仍可访问；无痕窗口可能自行销毁，按 sip 状态再次核对。
没有改变正常软件关闭群聊时的既有后台行为。
