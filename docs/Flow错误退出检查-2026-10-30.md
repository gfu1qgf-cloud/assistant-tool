# Flow 错误退出与停滞检查（2026-10-30）

检查版本：主程序0.6.35，桥接扩展保持1.1.62。本次没有修改浏览器控制方式或扩展，也没有操作真实Flow页面。

## 已复现并修正

1. `scheduler_recovery.watch` 原来将进入“提交中”视为进展，实际尚未得到网页接收确认。反复提交前失败会反复清空停滞恢复计时；生成与下载状态切换也会重复计入进展。现在只记录每个任务执行号首次确认接收、首次进入结果阶段两个里程碑，不把发送动作或同一次下载重试算作新增进展。记录随任务删除或执行号更换而清理。
2. `fault_rotation.healthy_remaining` 原来可能把已启动但超时未连接、实际不能再次派发的配置当作健康候选，令已安全关闭的故障账号一直等不到下一轮。现在仍在有效启动期内的配置与未尝试配置保持原优先级，过期且被启动记录禁止再次派发的配置不再阻挡换号。原物理窗口占位保留，不能把断线或启动超时视为已关闭窗口。
3. 自动恢复失败后的详情补列未连接的具体Profile、启动或断线状态及需要检查的扩展／项目，避免只显示窗口数量却无法定位。

## 核对的退出路径

| 路径 | 现有退出行为 |
| --- | --- |
| 普通请求、准备、上传和关闭无响应 | `_tick`按对应请求超时处理；准备未提交时换号或有界恢复，传输使用独立重试策略，关闭未确认时保留原窗口占位。 |
| UI锁持有者不再进展 | 有效期结束进入停止流程；支持续期的持有者未在5秒内确认停止时，断开其本机WebSocket后交接。续期只接收限定的成功步骤；单纯等待或失败不续期。 |
| UI锁排队 | 排队与实际操作计时分开；允许继续等待与重排，不能把排队本身当生成进展。 |
| 首次连接／积分读取 | 浏览器准备时间与读取次数有上限；已停用账号不继续占其他任务的准备名额。 |
| 原视频下载失败／绑定缺失 | 独立计数、核对后暂存或跳过下载，保留原结果，后续生成继续。 |
| 已提交生成但结果不明 | 只读核对达到上限后保留为待核对，不擅自再次付费生成；其他符合条件的账号继续。 |
| 全局无派发进展 | 默认观察30秒后进入两轮恢复，两轮之间45秒；仍不能恢复时通知并给出原因。发送提交、反复探测和状态来回切换不再重置这次事件。 |

## 验证边界

使用独立副本、临时SQLite任务、模拟浏览器连接及可控时钟检查。新增回归覆盖未确认提交反复发生、下载状态来回切换、超时启动不阻挡换号、有效启动仍受保护及物理占位不被误释放。相关回归共177项，176通过、1项跳过。静态查询使用本机独立codeTree定位，再逐段核对源码；静态候选关系不作为执行成功证据。

这不是所有运行环境下绝无停滞的证明。登录、验证码、权限、积分、磁盘或用户标签页保护等条件无法自动解除时，程序需要保留原任务和限制，并明确显示原因；不能用重新生成或强行释放未确认退出的窗口来伪装进展。
